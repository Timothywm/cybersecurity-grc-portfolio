# 01 · Detection Engineering Report

**Engine:** Snort++ 3.12.x (passive IDS mode) · **Sensor:** Kali Linux VM · **Ruleset:** `rules/local.rules` (rev 2)

## 1. Method – detection lifecycle applied to every rule

```
Threat / ATT&CK technique → Detection hypothesis → Rule → Syntax gate (snort -T)
   → True-positive test → False-positive baseline → Evasion test (FN) → Tune → Document & version
```

A rule is only "done" when it has evidence for all three outcomes: it **fires** on the attack, **stays quiet** on
look-alike benign traffic, and its **evasion limits are known and written down**. Results are generated by
`scripts/05_collect_evidence.sh` into [`evidence/results.md`](../evidence/results.md) – nothing in this report is hand-typed data.

## 3. Engineering decisions (what changed from rev 1 and why)

| # | Rev 1 | Rev 2 | Reason |
|---|---|---|---|
| 1 | `flags:S*` | `flags:S` | In Snort 3 `*` = *any* of the listed flags, so SYN/ACK matched too. A scan is an initial SYN only. |
| 2 | `alert tcp … any 80` + raw `content` | `alert http` + `http_uri` / `http_client_body` sticky buffers | Matches the **normalized** HTTP field (percent-decoding), works on any HTTP port the inspector identifies, avoids matching in response bodies. |
| 3 | one broad SQLi rule | two tiers (1000003 broad/triage, 1000006/7 high-fidelity) | Separates "worth a look" from "page someone" – the core mechanism for managing alert fatigue. |
| 4 | no alert cap | `event_filter` limit 1/60 s per source on rate rules | `detection_filter` alerts on *every* packet above threshold → thousands of duplicates per scan. |
| 5 | `any` destination | `$HOME_NET` | Rules protect the defined segment; set `HOME_NET` for production. |
| 6 | – | metadata + references | Traceability from alert → ATT&CK / OWASP / CWE for audit and reporting. |
| 7 | – | SID 1000008 telemetry | Turns an invisible risk (encrypted traffic) into a measurable number. |

## 4. Detection-methodology positioning (NIST SP 800-94)

All rules are **signature/threshold based** (stateless pattern + simple rate). The guide also describes anomaly-based and
stateful-protocol-analysis methods; this lab deliberately uses signatures for transparency and auditability. Rate rules are a cheap
approximation of behavioural detection; their failure mode (low-and-slow) is exactly why the SIEM correlation recommendation in
[05-risk-register](05-risk-register.md) exists.
